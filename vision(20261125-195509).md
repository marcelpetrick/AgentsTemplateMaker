# AgentsTemplateMaker vision

AgentsTemplateMaker will be a form on GitHub Pages for composing a project's `AGENTS.md`. A maintainer should be able to start with sensible rules, see exactly what each choice adds, write instructions in their own words, and hand the resulting file to a coding agent. The agent and user can refine those instructions together as the project evolves.

This document is the handoff for a future implementation. The current milestone is collecting the vision, deriving requirements, and challenging them before building. An earlier exploratory form exists. Its defaults, layout, and behavior carry no approval. GitHub Pages deployment is a future deliverable.

## Maintainer decisions

| Decision | Behavior and verification |
|---|---|
| Commit discipline | Preselect one rule combining Conventional Commits with atomic commits. Each commit addresses one topic, names the change, and refers to the requirement when one exists. Preselect the full-message length rule. Offer strict bounds of 300 and 600 characters. The initial choice between those two limits remains open. |
| Repository evidence | Preselect credential hygiene and traceability. Record new user inputs and decisions in version-controlled Markdown under the documentation directory. Link each decision and its rationale to requirements, implementation, and checks. Git supplies its timestamp. A reviewer should be able to reconstruct why the choice was made from a clean checkout. |
| Preferred design study | The maintainer prefers the light, rules-first mockup. Use it as the desktop design reference: project rules on the left, the editable `AGENTS.md` on the right, and Copy and Download beside the document. Carry the same layout into dark mode so controls stay familiar. |
| Editing and export | Unchecking an untouched rule immediately removes its paragraph. Unchecking an edited rule retains it as custom text and tells the user why. Track generated ranges and authored edits, including identical text in different locations. Warn during editing that unchecking will preserve the changed paragraph. Visibly mark user text in both themes. A green underline and a marker at the start of the affected paragraph are suggested treatments. Copy and download must use the current editor contents, including manual changes. |
| Languages | Provide English and German independently for both interface and generated Markdown. Recommend English for repository instructions. Changing output language regenerates untouched paragraphs. Keep authored text in its original language and warn before applying a change affecting edited rules. |
| Plain language | The maintainer referred to Andrej Karpathy’s “flight manual” idea to mean simple, plain English that people and agents can understand. Use familiar words, direct sentences, and concrete actions. Apply the same clarity when writing in German. |
| Conflicts and advisors | An advisor can recommend an interpretation. Agents may resolve clearly obsolete guidance, such as Python 2, by choosing the latest compatible, supported stable release (for example, Python 3). Where applicable, respect the project's long-term support policy. Record the reasoning. Escalate incompatible stakeholder requirements or changes to required behavior to a human. |
| Domain tooling | Offer domain-appropriate development tools, including Ruff for Python linting and Black for formatting. Select one formatter to avoid conflicting rewrites. Pin dependency versions, review updates regularly, and take compatible updates after verification. Document blocked updates and the requirement or failing check that prevents them. |
| From-scratch verification | Provide a pipeline that starts from a clean clone, obtains pinned dependencies, configures the environment, builds the implementation from repository sources, runs every applicable pipeline job, and checks its results. Document external prerequisites and required secret names. Verify all declared build targets without relying on unstaged files or a developer machine. |
| Development order and architecture | Apply TDD to AgentsTemplateMaker itself and offer it as a generated instruction. For example, first write a failing test that unchecking an edited rule preserves its exact text. Then implement that behavior and run the test again. Document AgentsTemplateMaker’s architecture with C4 views drawn in Mermaid, and offer both conventions in the rule catalog. |
| Remaining policy choices | A configurable minimum of 99% was suggested. Executable-line coverage with an opt-in gate is a proposal. The scope of the later repository scan, publication repository, exact versioning scheme, and organization-specific budgets remain project decisions. |

## What the maintainer asked for

| Input | Intent to preserve |
|---|---|
| I1 · Start small, then expand | Deliver a neat prototype on GitHub Pages. Offer preselected basics and build out the catalog after trying the form. Organize it from the highest-impact decisions down to details. |
| I2 · Compose in a real text field | Each checkbox contributes a paragraph to the visible Markdown. Checking or unchecking an untouched rule changes the text immediately. Users can type anywhere, revise a generated paragraph, or add independent instructions. Visually identify user-written text, for example with a green underline. Preserve it through unrelated changes. Warn before a form control would overwrite or remove an edited paragraph. Direct typing and deletion remain under the writer’s control. |
| I3 · Make the interface accessible in the user's language | Provide light and dark modes. Plan for multiple interface languages, initially English and German. Recommend English for repository content, including the generated file. Allow teams to choose their native language for generated instructions. |
| I4 · Explain choices in context | Give each repository instruction option a tooltip explaining its benefit and cost. Projects have different budgets. For example, concurrent sub-agents can shorten elapsed time or check more cases, while consuming more tokens. |
| I5 · Decide how the agent operates | Let maintainers choose whether to use sub-agents for parallel work, use lower-cost or less capable models, use advisor mode, seek user approval, or make routine decisions independently. Agent behavior comes before software construction details. |
| I6 · Describe how software is built | Capture preferred technologies. Favor open-source tools wherever feasible unless the project or user directs otherwise. Include a selectable software version-numbering policy. |
| I7 · Make repository history useful | Offer Conventional Commits, atomic commits covering one topic each, commit messages that identify the work they address, and a short limit for the whole message. Under 300 or under 600 characters were examples. Keep credentials out of commits and other project material. |
| I8 · Make instructions readable | Offer the “flight manual” approach to readability. The maintainer clarified this as using plain language that people and agents can understand. |
| I9 · Connect goals, changes, and proof | State the outcome the user needs, the requirement that follows, what implements it, and how to verify it. An independent agent starting without the conversation should be able to reproduce or challenge each claim about a change. |
| I10 · Catch errors early | Red-team requirements up front and every commit from the beginning. A wrong requirement causes rework even when the code implements it correctly. An implementation bug also costs time to repair, and a customer-reported defect is discovered later still. Scrutiny belongs at each stage. |
| I11 · Automate verification | Offer unit, integration, end-to-end, and acceptance testing, automated where feasible. Test every supported build target. Offer mutation testing of unit tests and a selectable minimum coverage threshold. At least 99% was suggested. |
| I12 · Learn from existing repositories later | In a later phase, scan the project's existing `AGENTS.md` files to assess which instructions proved viable, which did not, and which to carry into the catalog. |
| I13 · Domain tools and dependencies | Choose established tools for the domain, pin dependencies, take compatible updates, and record why a required behavior blocks an update. |
| I14 · Rebuild from source | Reconstruct the project from a clean clone. Acquire dependencies, configure, build, run the pipeline jobs, and inspect the results. |
| I15 · Test first | For every new behavior or bug fix, write the test before implementing the change. |
| I16 · Architecture diagrams | Document the architecture using the C4 model and maintain diagrams as Mermaid source in repository Markdown. |

## First walkthrough for the implementing agent

Open the light, rules-first design on desktop. Hover over **Repository practices** on the left. The category expands. Select a commit-message limit of 600 characters and watch the paragraph on the right update in place. Add a project-specific sentence to that paragraph, then uncheck the rule. The paragraph stays, its custom text remains marked, and the form explains why it was kept. Copy or download the file and compare it with the editor, including the added sentence.

## Prototype experience

The proposed order is **agent operating policy → software and technology choices → repository practices → verification details**. A maintainer can understand their delegation and approval policy before choosing an individual test threshold. On desktop, keep the editable document visible on the right while the user browses rules on the left. Opening a category reveals its choices. Selecting a rule changes the document immediately, without an Apply button or page reload. The prototype should demonstrate one complete path from preselected choices to a usable Markdown file. Use the confirmed selections in the implementation baseline below. The full catalog below records the intended scope beyond that first slice.

### Instruction catalog requirements

These are choices the form should offer. Selecting a rule writes a direction into the file. Actual enforcement and evidence belong to the repository and its agents. For each selectable policy, check its generated contribution in the export. Deselect an untouched rule and verify that only its generated contribution disappears, even when a user-authored paragraph has identical wording. Use the examples to judge whether the resulting instruction is specific enough to follow.

| ID · input | Choice to expose | Observable meaning in the generated instructions |
|---|---|---|
| C01 · I4, I5 | Parallel sub-agents | Distinguish omission (no delegation instruction), explicit prohibition, and permission within a stated scope. Export and inspect all three cases. Explain the trade-off using elapsed time, depth of independent checking, and token use. An agent can determine whether it may delegate a sample task. |
| C02 · I5 | Model choice and advisor mode | Configure lower-cost model use and advisor involvement independently. State which tasks qualify, when to consult an advisor, and who decides. An advisor provides a recommendation. A human resolves conflicting stakeholder requirements. |
| C03 · I5 | Approval or autonomy | Identify decisions an agent may make and decisions requiring user approval. A reviewer can classify a routine choice and an approval-bound choice from the text. |
| C04 · I6 | Technology preferences and open-source tooling | Record preferred technologies in the user's terms. Express the default preference for open-source tools wherever feasible and honor explicit exceptions. |
| C05 · I6 | Software version numbering | Name the selected versioning scheme and describe when to change the version. Semantic Versioning is a candidate. Confirm the scheme and release triggers. |
| C06 · I7 | Conventional Commits and change identification | Couple Conventional Commits with atomicity. Offer decision traceability as an additional default. A selected format rule gives a valid example such as `fix(parser): handle an empty field`. A selected traceability rule identifies what change or requirement the commit addresses. |
| C07 · I7 | Atomic commits | Limit each commit to one coherent topic. A behavior change and its associated tests can form one commit. An unrelated formatting sweep belongs elsewhere. |
| C08 · I7 | Commit message limit | Express the chosen bound and whether it is strict. Proposed interpretation of “under 300” counts subject, body, footers, and internal line breaks and permits 299 characters. Offer both 300 and 600. |
| C09 · I7 | Credential hygiene | Keep credentials out of committed files, messages, examples, logs, and generated artifacts. Use placeholders in examples. Validate this instruction with synthetic fixtures. |
| C10 · I8 | Flight-manual readability | Use plain, direct language. A reader should be able to identify the requested action without decoding unexplained jargon. |
| C11 · I9 | Traceable and verifiable requirements | Link the intended outcome to a stable requirement, implementation change, acceptance criterion, and evidence. A reviewer can start from either a claim or a change and follow the connection. |
| C12 · I9, I10 | Adversarial review of requirements and commits | Instruct reviewers to look for ambiguous goals, counterexamples, missing failure cases, and unsupported claims. Record findings and dispositions for every reviewed commit. |
| C13 · I11 | Unit, integration, end-to-end, and acceptance testing | Offer four independently selectable paragraphs. Distinguish isolated behavior, interactions across boundaries, a complete user journey, and evidence that an agreed user outcome is met. |

## Development and independent verification

Apply this process to AgentsTemplateMaker itself from the first implementation commit. C11 and C12 also let other projects adopt it through their generated file.

1. Before coding, challenge each requirement against its originating input. Ask what implementation could satisfy the wording and still disappoint the user. Resolve material ambiguities with the maintainer.
2. For each atomic commit, use a review record outside that commit, keyed to its full immutable SHA (for example, a check run or review comment). This avoids creating another commit solely to record the review. Record its identifier, affected requirement IDs, exact behavioral claims, prerequisites, fixtures, reproduction steps, expected results, and evidence location. Record the supported environment and target matrix where relevant.
3. Give an independent agent the identified revision and that packet. They start from a clean checkout without conversation history or the author's working state. They reproduce the claims and try a counterexample. Distinguish observed results, failures, and checks they could not run.
4. Record review findings, their disposition, and the revision checked. A fix gets its own review. A failing or unverified claim stays open. When a defect is reported later, link it to the requirement, regression check, and corrective change.

AgentsTemplateMaker can meet its independent-agent review requirement in a fresh, sequential session when parallel delegation is disabled. In generated instructions, let each project choose its review policy. If its constraints prevent the requested independent check, record the claim as unverified.

## Independent requirements review

A reviewer read this handoff without the conversation history and identified three gaps. The draft now distinguishes an omitted delegation rule from a prohibition (C01), checks rollback of a change affecting multiple paragraphs, and ties review evidence to an immutable commit outside its own contents. The review assessed the written requirements. The prototype acceptance checks remain pending.

### Requirement challenge cases

| A plausible false pass | Evidence that would expose it |
|---|---|
| The editor removes the first matching paragraph, which happens to be the user’s identical copy. | Insert identical text above and below the generated rule. Uncheck the rule and compare both copies and their surroundings. |
| A warning appears on checkbox removal, yet a locale or threshold change silently regenerates several edited rules. | Edit two rules and insert a separate custom paragraph. Trigger a setting change that affects both rules, then cancel. Verify every character, selected setting, and authorship mark returns to its starting state. |
| The project reports a green CI run even though one supported target was skipped. | Compare named test results with the independently enumerated target matrix, including skipped jobs. |
| A project reaches 99% line coverage while tests miss an incorrect return value. | Use a fixture with a known expected return value. Mutate that return value and rerun the unit tests. If the tests still pass, record the missed behavior alongside the measured coverage. |
| A second agent repeats the author's summary while relying on an uncommitted local fixture. | Reproduce from the named commit in a clean checkout with only the documented prerequisites. Record the missing fixture as a failed reproduction. |

## Sequence

1. Review this vision and resolve the decisions needed for the first slice. Implementation is paused until the maintainer requests it.
2. Approve a prototype baseline with linked acceptance checks. Implement and verify it on GitHub Pages.
3. Try the form on real project decisions, then expand its rules, technologies, and languages in response to findings.
4. When authorized, scan the project's existing agent instructions and compare them with actual usage, review evidence, and maintainer feedback.
